# 冷启动与待恢复播放位置

2026-10-12，XW-75 的停止进程后 SearchLyricsIntent 冷启动小节已通过。该验收发现的 XW-89 播放位置丢失已在 `8877bee` 修复，并通过独立代码审阅、受控加载回归和新版本原生复验。XW-75 的其他系统与呈现条件仍单独保留。

## 实际缺陷与修复

旧执行源码 `3b44632` 的真实冷启动可以交付正确歌词 query、关闭面板并正常退出，完整 XCTest 为 Passed 1/0（4.089 秒）。但协调方复核停止后的数据库时发现，队列和聆听会话的保存位置都从 20,000 ms 变成 0。准备过程没有清零位置或发送 seek；JSON 队列内容相同并不能证明其标量位置保留。原本笼统的持久化通过描述已纠正，实际失败数据库继续保存。

`PlaybackService` 加载流之前把引擎位置设为 0，保存的 seek 要等异步加载完成后才应用。此时退出、睡眠、唤醒或更新检查点会把临时零写回队列和会话。受控暂停加载在修复前产生四种生命周期场景、八处持久位置断言失败，确认这是应用缺陷。

修复由当前加载序号和曲目身份共同拥有待恢复位置；会话检查点通过共享播放服务读取该位置。显式 seek（包括 0）可替换它，失败后的 Play/toggle 重试保留它，换曲不会继承它，成功加载后回到正常引擎时钟。统计关闭时仍保留队列恢复位置，既有会话统计开关保持原义。

独立审阅又发现两个视频交接时序：未就绪视频不能从临时零开始；原生加载迟到完成也不能把正在播放的视频从新位置拉回旧偏移。两条路径先复现九处失败断言后修复。当前视频继续拥有传输位置；视频先关闭与原生加载先完成的两种顺序均有覆盖。没有增加高频观察器、并行服务、模型迁移或权限。

最终定向回归通过 109 项、11 个套件（2.351 秒），覆盖会话/历史、加载/准备、外部路由、队列持久化、视频传输及更新。Release 编译通过（63.93 秒），匹配 App Intents 元数据已重新提取，四个改动文件与最终独立复审哈希一致。

## 新版本原生复验

使用 `8877bee` Release、匹配元数据、原有签名团队和全新隔离身份，在 macOS 27.0.1 / arm64 执行公开 AppIntentsTesting。签名完成后曾检测到新的锁屏，彼时请求和实际调用都是 0；用户确认本次解锁、现场预检通过后，沿用同一签名工件。

六个目标进程为零的检查点之后，仅派发一个请求、调用一次 `run()`。精确 bundle、应用路径和请求绑定一致；框架启动新 PID，歌词字段显示唯一 query，字段与 Close 均可操作。关闭后仍为同一曲目、暂停、音量 0，再立即正常 Command-Q。没有提前启动应用、替代 URL 路由或等待流加载完成。

完整 XCTest 为 **Passed 1/0**，方法耗时 4.727 秒、请求耗时 7.15 秒、退出码 0，无外层观察器中断或警告。`run()` 返回用时 1.475 秒，调用开始到发出正常退出为 4.416 秒，到确认进程消失为 4.672 秒。这些是本次实测时间，不是性能门槛。退出时引擎是否已完成加载未直接探测；待加载竞争由受控回归证明，原生阶段直接证明实际位置保留。

## 数据与独立复核

本次实际可写副本在调用前单独保存检查点，与原始 seed 的 SHA-256 完全一致，两处位置均为 20,000 ms。正常退出后、任何恢复或移除之前再次保存真实副本。协调方使用独立比较代码确认：

- 两处持久位置仍为 **20,000 ms**；8 个队列标量和除 ORM/更新时间外的 10 个会话字段一致。
- schema 和全部 27 张表已比较，21 张稳定表忽略 `Z_OPT` 后一致；655 首 Track、5 组导入/1,161 项、10 个修订和 60 条聆听事件保留。
- 7 个队列 JSON 字段语义一致；只允许原先缺失的 9 个 `historyRecordID` 经既有恢复路径补为互不重复的 UUID，其余内容和顺序一致。
- ORM 事务、主键簿记和保存时间变化单独记录，不把播放位置纳入忽略项。

协调方还从完整 xcresult 归档重新提取 summary，确认 Passed 1/0；独立核对 12 项保护哈希、原 seed 的 0400 权限、自有偏好恢复为空及物理文件消失。精确候选、runner、容器、数据/缓存和注册均清理，自有进程与窗口为零。用于独立提取的临时副本也已移除。正常应用、库和 Keychain 保留。

## 接受范围与证据
